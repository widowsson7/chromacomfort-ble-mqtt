# Firmware audit — flash size + correctness (2026-07-10, AZ)

Audit of `chroma_comfort_ble.ino` v1.5.0 (the uncommitted state after the
extended-unique-IDs + ArduinoOTA session). Result shipped as **v1.5.1** in this
folder, plus a new `build_opt.h`. Every number below is from a real
`arduino-cli compile --fqbn esp32:esp32:esp32` on the default partition scheme
(max app size 1,310,720 bytes). Line references are to the pre-audit file
unless marked "now".

**Verification status: compile-verified only.** v1.5.1 has NOT been flashed to
the device. Before trusting it in production, OTA it and confirm: (1) BLE
connects/reconnects to the fan (the NimBLE role trim is the least-proven
change), (2) commands work from HA, (3) `Acks` starts tracking `TX`. If acks
still stay at zero after the fix, that becomes evidence the fan doesn't send
`A0 40` frames at all (see finding B1's caveat).

## Task 1 — program storage

|---|---|---|---|---|
| 0 | Baseline v1.5.0 | 1,251,159 (95%) | — | 59,561 |
| 1 | v1.5.1 sketch changes only (CC_DEBUG=1) | 1,250,695 (95%) | −464 | 60,025 |

### What was tried and what it actually bought

- **NimBLE role trim (−17,164 vs row 1): the only meaningful binary win.**
  The sketch is a pure BLE central (connects by fixed MAC; never advertises,
  serves, or scans), so `build_opt.h` disables the peripheral, broadcaster,
  and observer roles at compile time. `build_opt.h` is a gcc response file the
  ESP32 core applies to every compilation unit in both IDE and CLI builds —
  flags only, **no comments allowed** (learned the hard way: comment lines are
  parsed as extra input files and kill the build).
- **Consolidating the 12 near-identical command senders into one
  `queueCommand()` (now line 225): −464 bytes net, i.e. almost nothing.**
  The linker was already folding the duplicate function bodies, and the v1.5.1
  bug fixes (spinlock, bounds check, reset-reason forensics, overflow handler)
  added code back. Worth keeping for maintainability, but it is not a size
  lever. Reported honestly: do not expect source-level dedup to buy flash here.
- **Serial logging behind `CC_DEBUG` (−3,776 when disabled):** all log strings
  and printf calls now compile out with `-DCC_DEBUG=0` in `build_opt.h`.
  Shipped **enabled** (behavior unchanged); the delta is available headroom,
  at the cost of blind USB serial.
- **Dead code:** `applyGammaCorrection()` was never called; removed. No
  separate delta — `-ffunction-sections`/`--gc-sections` was already
  stripping it from the binary.
- **Not worth pursuing:** ArduinoHA (every declared entity is real) and
  CORE_DEBUG_LEVEL (already 0 in this board config).
- **Candidates measured-not / for later, if headroom gets tight again:**
  - `-DCONFIG_BT_NIMBLE_CRYPTO_STACK_MBEDTLS=1` in `build_opt.h` — NimBLE
    docs claim ~8 KB when mbedtls is already linked (WiFi links it). Unmeasured.
  - **Partition scheme — the real lever.** *Minimal SPIFFS (1.9MB APP with
    OTA)* raises the app ceiling to 1,966,080 bytes (+655,360 headroom, +50%)
    and keeps OTA. Requires ONE USB flash (partition table can't change over
    OTA); after that OTA continues normally. This sketch uses no SPIFFS, so
    the shrunk 190 KB SPIFFS costs nothing. Recommended at the next
    physical-access opportunity, then binary-size games stop mattering.

## Task 2 — bugs / failure modes

### B1 — CONFIRMED: `Acks` sensor could never count (the live-test anomaly)

**Old code:** ack matching at old line 829 required `packet.len == 4 &&
tx.getCount() > 0`. But the send path (old line 815) pops the command off `tx`
immediately after its 3×37 ms write burst, in the same loop iteration. The ack
notification is processed on a LATER iteration, by which point `tx` is empty —
so the `tx.getCount() > 0` gate was false and the ack branch unreachable in
the normal one-command case. This is leftover logic from the original sketch's
design where the send path only `peek`ed and the ack was what popped. Exactly
matches the live observation: `tx` incremented, fan visibly obeyed, `acks`
stayed 0.

**Worse — the same block dropped real commands:** when a second command WAS
queued (e.g. two quick dashboard actions), the gate passed and old line 835's
`tx.pop(&packet)` threw away the *next, unsent* command. Concrete failure:
toggle fan then light within ~100 ms → fan command sends, its ack pops the
light command → light never changes, no error anywhere.

**Fix (now lines 824, 847):** ack matching keyed only on the frame shape
(`len==4`, control bytes `A0 40` per README); the double-pop is gone. An
`awaitingAck` flag counts acked *commands* rather than ack *frames*, since the
fan may ack each of the three writes — without it the counter could triple-count.

**Caveat, stated plainly:** we have no capture proving this fan actually emits
`A0 40` frames (the old counter couldn't have counted them even if it did). If
`Acks` still sits at zero after v1.5.1, the protocol-doc assumption is what's
wrong, not the queue logic. The panic-flush heartbeat condition was left
byte-for-byte as before (only counts while `tx` is non-empty) specifically to
avoid betting live behavior on unverified ack delivery.

### B2 — rx queue is shared across tasks with no locking (real race)

`onBLENotify` runs in the **NimBLE host task** (GAP event
`BLE_GAP_EVENT_NOTIFY_RX`, NimBLEClient.cpp:1165 dispatches the subscribe
callback there), while `loop()` pops `rx` from the Arduino loop task. cppQueue
has zero internal locking; `push`/`pop` both do unguarded read-modify-writes
on `cnt`/`in`/`out` (cppQueue.cpp:123–185). A collision can lose or double an
update: symptoms range from a phantom/stale packet to `cnt` drifting until the
queue reads permanently full — after which every status notification is
silently dropped and HA stops tracking wall-switch changes until the next
reboot. Low per-iteration probability, but the fan notifies many times per
second, 24/7. **Fix (now lines 365, 832):** `portMUX_TYPE` spinlock around
both rx accesses; critical sections are a 19-byte memcpy. (`tx` needs no lock —
all its touches are in the loop task.)

### B3 — unchecked wire length byte → stack buffer overflow

Old line 378: `createPacket(pData[0], pData + 2, pData[1])` memcpys a
wire-supplied length (0–255) into `Packet.data[17]` on the NimBLE host task
stack, and reads up to 253 bytes past the actual notification payload. One
corrupted/malicious notification with `len > 17` smashes the host task stack —
at best a panic-reboot (which this device masks well), at worst silent memory
corruption. **Fix (now line 359):** reject frames where `dataLen > 17` or
`dataLen + 2 > length`.

### B4 — tx queue overflow drops commands silently

`tx.push()` returns false and discards the newest item when 25 commands are
queued (overwrite=false), and no call site checked it. Realistic path: fan
unreachable (BLE down), HA/user keeps issuing commands → everything past #25
vanishes with no log and no counter. **Fix (now line 239):** failed push logs
and increments the Errors sensor. (Related pre-existing behavior, documented
not changed: commands queued during a BLE outage longer than ~6 s are
panic-flushed shortly after reconnect — the queue is not a replay buffer.)

### B5 — "Last Restart Reason" lies after hard resets

`saveCrashInfo()` only runs on *soft* restart paths. A task-WDT panic,
brownout, or power cycle reboots without writing NVS, so the next boot
re-read the *stale* reason from an older soft restart and presented it as
current — misleading in exactly the forensic scenario the sensor was built
for (a WDT reset, the one case with no other trace). **Fix (now line 584):**
the saved reason is one-shot (removed after read); when absent, the sensor
reports the silicon's `esp_reset_reason()` code (1=poweron, 3=sw, 4=panic,
5=int-wdt, 6=task-wdt, 9=brownout). Note the sensor's semantics change
slightly: a reason now describes only the immediately-previous restart.

### Checked and found SAFE (no action)

- **OTA vs hardware watchdog:** verified in ESP32 core 3.3.10 source
  (`ArduinoOTA.cpp` `_runUpdate()`): the receive loop invokes `onProgress` —
  and therefore our `esp_task_wdt_reset()` — after every ≤1460-byte chunk,
  and a stalled sender is aborted by ArduinoOTA itself after ~4 s (1000 ms
  `_ota_timeout` × 3 retries), nowhere near the 60 s WDT. `Update.end()`'s
  MD5 verify is also far under 60 s. The one WDT reset per chunk is
  sufficient at any transfer speed.
- **BLE reconnect vs MQTT keepalive:** worst-case `loop()` stall is the 10 s
  BLE connect timeout (NimBLE 2.x `setConnectTimeout` confirmed to take
  milliseconds) plus service discovery. PubSubClient keepalive is 15 s and
  brokers allow 1.5× (22.5 s), so a single blocking attempt can't kill the
  session; attempts recur at most every 5 s so `mqtt.loop()` always runs
  between them. Margin is thin but real, and self-heal (120 s MQTT threshold,
  ~12 ArduinoHA reconnect attempts at its 10 s interval) backstops it.
- **Self-heal vs WDT interaction:** WDT (60 s) > longest legitimate loop
  blockage (~10–15 s); self-heal thresholds (60/120/90 s) operate on
  wall-clock health, not loop liveness — no overlap where one starves the
  other. `millis()` rollover types are sloppy (`int lastUpdateAt`,
  fixed to `unsigned long` in passing) but unreachable: the 24 h proactive
  reboot fires 25 days before any wraparound.
- **Design tradeoff noted, not changed:** a fan powered off for hours makes
  the bridge reboot every ~90 s indefinitely (BLE self-heal), each cycle
  writing 7 NVS keys. NVS is wear-leveled; at ~960 cycles/day this is fine
  for outage-days, just don't leave the fan breaker off for months.
